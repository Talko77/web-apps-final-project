Start here · HTML response

1. The user enters /

The browser asks the server for a page. The server reads MongoDB, prepares data, and renders views/pages/public/home.ejs. EJS is a template that produces HTML; the browser receives its rendered result, not the EJS source.

The initial homepage does not call the feed API. Its controller queries the Article model directly. Later browser interactions call /api/articles/feed and receive JSON.
The two initial database results
ResultDatabase operationUsed by
feedPublished articles, { publishedAt: -1, _id: -1 }, limit 20; populate reporter name.All Articles grid; the same mapped cards supply the lead, next 2 Featured Stories, and next 8 Latest Dispatches.
mostReadPublished articles, totalViews descending, limit 5; select title, category, and views.Most Read sidebar.

The public content comes from publishedVersion. An already published story can still appear while its newer draft is under review: visibility depends on isPublished, rather than the draft’s workflow status.

What exactly does the controller pass to home.ejs? 
res.locals.currentUser = req.session.user || null

res.render('pages/public/home', {
  pageTitle: 'The Daily Web — News',
  editionLabel: /* formatted server date */,
  showBreaking: true,
  breakingText: 'Demo edition — all content on this site is sample data for the course project',
  searchQuery: '',
  categories: ['World', 'Business', 'Technology', 'Science',
               'Culture', 'Sports', 'Opinion'],
  featured: /* up to 3 formatted cards */,
  dispatches: /* up to 8 compact story objects */,
  mostRead: /* up to 5 title/category/views/link objects */,
  feed: /* up to 20 formatted cards */,
  hasMore: feed.length === 20
})

Locals are named values that EJS can read while creating HTML. This object stays on the server; it is not sent to the browser as a JSON response.

2. What loads into this HTML page?

The template includes reusable fragments on the server. Their markup becomes part of one HTML response. The browser then requests the CSS and JavaScript referenced in that response.

views/pages/public/home.ejs
├─ partials/shared/head.ejs
│  ├─ charset, viewport, title, description
│  ├─ /css/style.css
│  └─ /js/api.js [defer]
├─ partials/public/header-standard.ejs
│  └─ partials/shared/site-logo.ejs
├─ main: lead + featured + dispatches + feed + sidebar
│  └─ partials/public/article-card.ejs [featured + initial feed]
├─ partials/public/footer.ejs
├─ /js/feed.js [defer]
└─ /js/weather.js [defer]

style.css imports Google Fonts and Material Symbols, then variables.css → base.css → utilities.css → components.css → layouts.css → pages.css. The browser may request font files from Google separately. Card images use loading="lazy"; the lead image does not.

api.js defines getJSON, sendJSON, escapeHtml, and flash, and attaches shared logout behavior. Loading this script does not itself fetch the feed or current user.

Sources: home.ejs · head.ejs · style.css · api.js

7. Lead story

The controller receives the article document and populated reporter, then creates a display object with title, summary, imageUrl, category, author, dateLabel, readLabel, views, and url. Reading time is estimated at 200 words per minute, rounded, with a minimum of 1 minute.

If there is no published story, the entire lead block is omitted. The image is loaded from imageUrl by the browser, not returned as image bytes in the page controller’s data.

10. All Articles: the initial cards

The feed and lead/featured/dispatches share one query and one mapped card array, so the headline stories also appear in the feed. Category options come from config/constants.js, not an API.

Session reading state is included immediately: the homepage wraps toCard() results with seen, using req.session.viewedArticles. Initial feed and secondary featured cards therefore render the same data-seen state and “Read” badge as API-loaded cards. The lead and dispatch markup do not display a read badge.

If there are zero published stories, the grid is empty, hasMore is false, and the initial status message is hidden. The “No articles match your search” message is shown after an API load returns an empty grid, not during this first render.

Sources: home and toCard · feed grid and controls · feed initialization · FEED_PAGE_SIZE and CATEGORIES

11. All Articles: search, filters, and sorting

Every feed control uses the same request-and-render flow. A filter change requests page 1 and replaces the cards in #feedGrid. The homepage URL and the other components stay as they are.

Each control’s exact request and server behavior
Component / hookQuery parameterWhat the server does
Search the feed
#feedSearch		search=climate
Omitted when blank.		Match publishedVersion.title with an escaped, case-insensitive regular expression. Searches titles, not article bodies.
Category
#feedCategory		category=Technology
Omitted for All Categories.		Match publishedVersion.category if the category is in CATEGORIES. Unknown categories are ignored.
Sort by
#feedSort		sortBy=publishedAt or sortBy=popularityNewest: publishedAt descending, then _id descending. Popular: totalViews descending, then publishedAt descending, then _id descending. The ID breaks ties deterministically. Unrecognized sort values use newest.
Reading status
#feedSeen		seen=seen or seen=unseen
Omitted for All.		Use IDs from req.session.viewedArticles: $in for Read, $nin for Unread. This works for guest sessions too.

Example request with several controls selected:

GET /api/articles/feed?page=1&search=climate&category=Science&sortBy=popularity&seen=unseen

Filters combine: this asks for unread Science stories whose titles match “climate”, with the most viewed first. The server derives reading history from the session; the browser does not submit a list of read IDs.

Search the feed — its own component flow
Category — its own component flow
Sort by — its own component flow
Reading status — its own component flow

Changing filters during a slow request: replacement loads run even while another request is loading. Each increments requestId; only the newest request may insert cards, show an error, or clear loading. Older responses are ignored, though their network requests are not aborted. Infinite-scroll append loads remain blocked while loading. Search invalidates an older request when its 300 ms debounce starts the new load.

12. All Articles: infinite scroll

The sentinel can trigger soon after page load if it is already within the observation area; scrolling is not required in that situation. This is the only way the initial feed starts a feed API request without a control change.

hasMore means “this batch contained 20”, not “the server counted another page”. If there are exactly 20 matches, the next request returns an empty batch, sets hasMore: false, and shows “You have reached the end of the feed.”

Without IntersectionObserver, the script does not attach infinite scroll and has no “Load more” fallback. The initial cards still display. After loads, the original data-page / data-has-more HTML attributes stay unchanged; the updated state lives in the script’s variables.

Sources: observer and load · getFeed pagination

14. Weather widget

The initial HTML contains an empty <div id="weatherWidget">. Unlike the stories, weather content is filled after JavaScript runs.

Illustrative fresh response:

{
  "source": "api",
  "ageSeconds": 0,
  "data": {
    "city": "Tel Aviv",
    "temp": 27,
    "feelsLike": 29,
    "humidity": 65,
    "condition": "clear sky",
    "icon": "01d"
  }
}
The four weather response paths
sourceWhat data is returned?What appears?
apiFresh normalized external result; ageSeconds: 0.Temperature, city, condition, feels-like, humidity.
cacheResult younger than 15 minutes; calculated ageSeconds.Same display. The script does not show the age.
stale-cacheOld cached result after a failed lookup or during its 60-second cooldown; no ageSeconds field.Same display plus “Data may be stale”.
fallback{ city: 'Tel Aviv', temp: null, condition: 'Weather data is unavailable right now', icon: '01d' }-- temperature, unavailable text, and “Data may be stale”.

The external service’s API key stays on the server. Weather is not stored in MongoDB; the cache disappears when the Node process restarts. The response contains icon, but the widget does not render it.

The script makes one request per page load; it does not refresh itself every 15 minutes. That duration controls server cache freshness. External lookup failures return fallback/stale JSON successfully; a failure to reach the app’s weather endpoint instead triggers the browser catch handler and shows “Weather data is unavailable right now.”

Sources: weather.js · weather route · weatherController.js

17. What happens when a story opens?

The lead, featured cards, dispatches, feed cards, and Most Read titles all point to /articles/:id. Following a story link starts a page request, not GET /api/articles/:id (that API serves staff editing/review).

View increments run without delaying the article render; repeated article-page visits also count as views. Returning with a fresh GET / re-queries the homepage, subject to those asynchronous increments completing. Initial feed and secondary featured cards now reflect the saved session reading history. The article view increment uses { timestamps: false }, so reading does not alter the article’s updatedAt or reorder newsroom lists.

Sources: article page route · articlePage · session-aware feed query

18. Loading, empty, and error outcomes

Failures and their boundaries
SituationResponse / screen behavior
Homepage database query throwsasyncHandler → errorHandler; normally HTTP 500 with the server-rendered error page rather than the homepage.
Feed database query throwsHTTP 500 JSON { error: 'Something went wrong on our side. Please try again later.' }; message appears in #feedStatus.
Feed HTTP request failsapi.js uses the JSON error message, or Request failed (status) if unavailable. Network errors also reach the feed catch handler.
Filter returns no cardsAfter a successful replacement, show “No articles match your search.”
Feed has no next pageShow “You have reached the end of the feed.” and stop observer requests while hasMore is false.
OpenWeatherMap is unavailableReturn stale-cache/fallback JSON; update the widget with a stale-data note.
App’s weather endpoint cannot be fetchedDisplay the weather-unavailable message in the widget.
JavaScript is disabledInitial stories, Most Read, header, footer, story links, header GET search, and native mobile menu work. Feed filters, infinite scroll, and Sign Out do not run; weather stays empty.

api.flash() does not clear its message on a timer; the feed controls its next status update. All feed updates are confined to #feedGrid and #feedStatus.

Learning checkpoint

19. Trace it yourself in the browser

  1. Run the app and open /. In DevTools → Network, reload. Find the document request for / and open its Response: the lead and initial article cards are already HTML.
  2. Find api.js, feed.js, weather.js, style.css, and the imported CSS/font/image requests. Filter by Fetch/XHR to find /api/weather.
  3. Type in Search the feed. After the debounce, inspect /api/articles/feed?page=1...: query parameters are the inputs; its JSON articles are the outputs. Watch only the All Articles cards change.
  4. Change category, sorting, and reading status one at a time. Compare their parameter names and response cards against the table above.
  5. Clear filters and scroll near the bottom. Inspect page=2. New cards append instead of replacing the grid.
  6. Open a story, return to the homepage, and select Read. The next feed API response should include that story with seen: true, and its initial homepage card should already have a Read badge.
  7. Submit the header’s Search the site form. Observe a document request for /search?q=... and a URL change.
Four questions to ask for every component: What triggers it? Which route/controller/script handles it? What data does it receive? Which HTML or DOM elements change?
