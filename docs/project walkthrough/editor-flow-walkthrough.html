Route and authorization

1. Entering the editor dashboard

The editor dashboard is /editor/reviews. /editor redirects a stored Editor session role there; other stored staff roles go to the reporter dashboard; guests go to login with the review queue as next. This convenience alias uses the stored role; the protected destination checks the current database role.

The real page route runs isEditor before editorQueue. It takes the account ID from the session and rereads User.findById(sessionUser._id).select('role').lean() on each protected request. A missing-session HTML request redirects to /staff/login?next=%2Feditor%2Freviews; a deleted account triggers session destruction and that login redirect. A current database role other than Editor receives a 403 error page. An allowed check refreshes the stored session role. The manage API uses the same middleware but returns JSON 401/403, including “Your account no longer exists” for deleted accounts.

Sources: models/User.js, middleware/errorHandler.js, server.js, routes/pages.js, middleware/auth.js, controllers/pageController.js, routes/articles.js.

Server rendering

2. Initial query, counts, and HTML

The controller awaits buildQueueQuery(req.query) from utils/queries.js, shared with the manage JSON API. The helper accepts valid raw status values draft, pending, published, returned; missing/invalid status means All. A valid category matches either draftVersion.category or publishedVersion.category. Nonblank search performs a User lookup on displayName/username and combines matching reporter IDs with both headline versions.

It then runs three Article operations in parallel: matching rows sorted updatedAt descending, capped at QUEUE_PAGE_SIZE=200 and populated reporter; a system-wide status aggregate; and countDocuments for all matching records. Rows become toQueueRow view models. The controller supplies pageTitle, newsroomRole=Editor, and page locals for controls, categories, rows, matching total, cap flag, and status totals.

The initial table is server-rendered. editorQueue.js attaches handlers but makes no initial manage request. The default query is empty, so Draft, Pending Review, Published, and Changes Requested can all appear. There is no default pending-only constraint.

Sources: utils/queries.js, controllers/pageController.js, config/constants.js, models/Article.js, models/User.js, utils/viewMappers.js, views/pages/editor/review-queue.ejs.

Template and assets

3. What loads into the document

The page includes shared head and newsroom header, then its queue intro, filters, table, empty message, and page-owned footer. Head loads /css/style.css and deferred /js/api.js. Deferred /js/editorQueue.js appears last and uses window.api.escapeHtml and getJSON.

style.css imports external font resources then variables → base → utilities → components → layouts → pages. Queue-owned rules live in pages.css. The table has a 1040px minimum width within a horizontal scroll wrapper; filters switch to a row at 640px, and the heading switches to a row at 1024px. Shared header rules remain in components.css. The script captures queueTable/tbody, queueSearch, categoryFilter, statusFilter, resetFilters, queueEmptyState, queueCount, queueTotal, and queueCapNote. It does not poll, load weather, or call /api/auth/me.

Sources: public/css/pages.css, public/css/components.css, views/pages/editor/review-queue.ejs, views/partials/shared/head.ejs, views/partials/newsroom/header.ejs, public/css/style.css, public/js/editorQueue.js, public/js/api.js.

Shared component

4. Header logo, links, and identity

For the Editor session, the logo and Review Queue link go to /editor/reviews, Analytics goes to /editor/analytics, Staff goes to /editor/staff, and View Public Site goes to /. The role badge uses newsroomRole; the name uses currentUser.displayName. All links perform ordinary document navigation.

Analytics and staff management are separate pages, not panels fetched by this queue. Sign Out is documented below. Header visibility does not grant authorization; each destination has its own route checks.

Sources: server.js, views/partials/newsroom/header.ejs, views/partials/shared/site-logo.ejs, routes/pages.js.

Components

5. Intro, matching count, and cap note

The intro renders Newsroom, Review Queue, and an explanation about submitted stories. The implementation’s default list includes all statuses. queueCount shows returned rows; queueTotal shows the true number matching current filters. For example, 200 of 237 articles triggers “Narrow the filters to reach the rest.”

There is no next page, offset, load-more action, or infinite scroll. Filtering is the only queue control for reaching records outside the first 200. The read/count operations are separate, not a transaction snapshot, so concurrent writes can affect consistency between totals and rows.

Sources: controllers/pageController.js, controllers/articleController.js, config/constants.js, views/pages/editor/review-queue.ejs, public/js/editorQueue.js.

Component

6. System-wide status summary

Summary spans show All, Draft, Pending Review, Published, and Changes Requested counts from the unfiltered Article aggregate. The Status dropdown repeats these counts. They describe all articles in the system, not the current category/search subset.

The spans are not filter buttons. Ajax updates replace the table and matching total only; status summary spans and dropdown count labels remain the initial snapshot. The API returns totalInSystem but the queue script does not consume it or refresh per-status totals.

Sources: controllers/pageController.js, controllers/articleController.js, views/pages/editor/review-queue.ejs, public/js/editorQueue.js, config/constants.js.

Component

7. Headline or reporter search

Each input event cancels the previous search timer and schedules reload after 250 ms. reload trims the value and sends nonblank search through URLSearchParams. This is server-backed search, not local row hiding.

Shared buildQueueQuery calls escapeRegex from utils/queries.js and uses case-insensitive regex matching on both draft/published titles and User displayName/username. Matching User IDs become a reporter condition. Category and search conditions are appended to query.$and, with alternatives within each condition combined with $or; valid status is a separate equality predicate. A result can match a published headline or category even when the visible row displays the draft.

Sources: utils/queries.js, public/js/editorQueue.js, controllers/pageController.js, controllers/articleController.js, models/User.js.

Component

8. Category selector

All Categories uses an empty value; the other options are the seven configured categories. Change immediately calls reload with the current search and status. The server validates known categories and matches either draft or published category.

The HTML controller’s activeCategory local retains the raw query value, whereas the database ignores an invalid category. An invalid value may not match any option; the browser selection can therefore differ from the supplied query. Normal UI choices use valid options.

Sources: utils/queries.js, views/pages/editor/review-queue.ejs, public/js/editorQueue.js, controllers/pageController.js, controllers/articleController.js, config/constants.js.

Component

9. Status selector

Options use raw status codes, unlike the Reporter dashboard’s human-label data filters. All has value empty. Selecting a status immediately requests fresh rows. Invalid status query values are normalized to All by the HTML controller and ignored by the API query builder.

The queue shows all statuses when All is selected. The actual label is mapped from each raw status, but the EJS and browser row templates always use status-badge--pending and state-loading indicator markup, even for Draft, Published, or Changes Requested. The mapper’s statusClass is not inserted into this badge.

Sources: utils/queries.js, views/pages/editor/review-queue.ejs, public/js/editorQueue.js, controllers/pageController.js, controllers/articleController.js, utils/viewMappers.js, config/constants.js.

Component

10. Reset Filters

The button sets all three controls to empty and calls reload immediately. Success shows the default all-status/all-category queue and replaces the URL with /editor/reviews. It does not navigate or clear session data.

Reset does not cancel the search debounce timer held in the input listener. If a search timer is still pending, it can later issue another request using the now-empty controls. A selector change while a search timer is pending has the same potential extra request.

Sources: views/pages/editor/review-queue.ejs, public/js/editorQueue.js.

API

11. Manage API and response contract

GET /api/articles/manage runs isEditor before getAllForEditor. It awaits the same buildQueueQuery(req.query) helper as the page controller, then performs the capped populated Article query, global aggregate, and matching count. getJSON sends Accept: application/json and same-origin credentials, with no body.

The response includes total, totalInSystem, hasMore, and articles. Each item is now solely the result of articles.map(toQueueRow), matching the initial EJS row contract. The previous raw-record spread was removed: raw _id, draft/published bodies, and hasPendingUpdate are absent. Mapped id and isUpdate remain; statusClass is returned even though the row templates do not apply it.

Components and mapping

12. Reporter, headline, summary, and category cells

toQueueRow chooses draftVersion when it has a truthy title, otherwise publishedVersion or draftVersion or empty object. This differs from the Reporter dashboard’s published-first mapping. Headline falls back to (Untitled article); category to Uncategorised. Summary/read time use the chosen version.

The shared reporterName(article) helper supplies populated displayName or username, else Unknown when the reporter account was deleted. Initials take up to two words. Beat is a label derived from chosen category (“Science Desk”) or Newsroom; it is not a stored user assignment. A pending article with isPublished=true gets the update badge.

EJS escapes initial values. rowHtml uses api.escapeHtml for later values in text/attributes, then render assigns tbody.innerHTML to all rows. No local sort, thumbnail, owner-only filter, or inline workflow button is present.

Sources: utils/viewMappers.js, views/pages/editor/review-queue.ejs, public/js/editorQueue.js, controllers/articleController.js.

Components

13. Version and Submitted cells

Version derives from publishEvents.length: no approvals → v1.0 Draft; published+pending → v(approved+1).0 Draft (Update); otherwise v(approved).0. It is a publication-count label rather than an autosave revision counter.

Submitted uses updatedAt, not a distinct submitted timestamp. The absolute label, ISO time datetime, and relative label are computed on the server; draft saves and other workflow saves can also affect updatedAt. Public reader visits now increment totalViews with {timestamps:false}, preserving updatedAt and queue ordering instead of making a visit look like a submission. Read time is rounded words/200 with a minimum of one minute. Labels have no browser ticking timer and refresh only when data is reread.

Sources: controllers/pageController.js, utils/viewMappers.js, models/Article.js, views/pages/editor/review-queue.ejs, public/js/editorQueue.js.

Components and destination

14. Headline and Review links

Both anchors go to /editor/reviews/:id for every row, not only pending rows. That route runs isEditor, finds the article by ID, populates reporter, and renders the side-by-side review page. Missing records go to 404; malformed IDs reach error handling.

The queue links do not approve, return, publish, edit, or delete. Those actions belong to the individual review page and its APIs. This chapter traces the navigation boundary; see the individual review walkthrough for the destination workflow.

Sources: views/pages/editor/review-queue.ejs, public/js/editorQueue.js, routes/pages.js, controllers/pageController.js.

Browser architecture

15. Row replacement, URL state, and overlapping requests

Each reload increments activeRequest and snapshots control values. After success, only the newest started request may update the DOM. It replaces rows, visible count, matching total (when non-null), cap note, then history.replaceState to /editor/reviews with the same query. Requests are not aborted and controls remain enabled.

replaceState makes the successful filter state shareable/reloadable but does not create one Back entry per filter. popstate reads the URL into the controls and triggers a request. No explicit loading indicator, disabled filters, or optimistic hide occurs; old rows remain during loading.

A typed search does not increment activeRequest until its 250-ms timer starts reload. An older in-flight response can still render during that debounce interval. Once a newer request starts, older successes and failures are ignored.

Sources: public/js/editorQueue.js, public/js/api.js.

Components and error paths

16. Empty results and failed requests

Initial empty-state visibility comes from page.articles.length, so it works without JavaScript. After success, render toggles queueEmptyState according to returned rows. Zero results show “No articles match the selected filters.” Table headings stay present.

On a latest-request failure the script only console.error logs “Failed to reload review queue”. Existing rows, counts, cap note, and URL remain; edited control values stay changed, which can leave controls inconsistent with displayed rows. There is no visible error paragraph, retry button, login redirect, or automatic retry. A later input/change/reset can retry.

The helper uses JSON error text for 401/403/500, or Request failed (STATUS) for a non-JSON error. A fetch failure or null successful response also reaches catch. An initial page-controller failure produces an HTML error document instead of a working queue.

Sources: views/pages/editor/review-queue.ejs, public/js/editorQueue.js, public/js/api.js, middleware/auth.js, middleware/errorHandler.js, controllers/pageController.js.

Shared component

17. Sign Out

api.js delegates #logoutBtn clicks, disables it, and posts /api/auth/logout without a body. The server destroys the session and clears connect.sid. Success JSON {success:true,redirect:"/"} leads to location.assign home. Failure simply re-enables the button; the queue shows no sign-out error.

Sources: views/partials/newsroom/header.ejs, public/js/api.js, routes/auth.js, controllers/authController.js.

Component and fallback

18. Footer and no-JavaScript behavior

The page-owned footer is static “The Daily Web · Newsroom · Editor’s Desk”. It has no request/listener.

Without JavaScript the initial server-filtered table, counts, cap note, empty message, and ordinary links work. Filter controls are not a submitted form, so changing them or clicking Reset does not update results. URL query parameters can still be supplied through normal navigation to obtain server-filtered HTML. Sign Out has no native form fallback. No-JavaScript access checks still run on the server.

Sources: views/pages/editor/review-queue.ejs, public/js/editorQueue.js, public/js/api.js, controllers/pageController.js.

Learning checks

19. Verification and learning steps

With safe local test data, inspect the document request and initial rows. Type a search and observe the 250-ms debounce, then select category/status and inspect GET /api/articles/manage. Watch the table replacement, count/cap change, and URL replacement. Compare summary totals before and after filtering. Open a Review link separately to distinguish document navigation from filtering.

Verification performed for this update: static review of the baseline branch diff and current page/API routes, database-role middleware, shared query builder, controllers, models, active EJS partials, browser scripts/helpers, and CSS ownership. Source and fragment links were validated. No browser, mocked-controller, or live-database tests are claimed for this update.

Limits: no browser layout run, real database regex execution check, live session persistence exercise, or concurrent database consistency test was performed for this page update. Only this documentation HTML was edited. Individual review, analytics, and staff pages remain separate chapters.
