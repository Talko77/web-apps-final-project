Navigation

1. Entering the login route

The canonical URL is /staff/login. It is a public GET route, so guests can see it. /login is an alias that redirects to it while preserving the query string. A guest requesting a protected newsroom HTML page is redirected to /staff/login?next=…; protected API requests instead receive JSON 401. Protected role middleware now takes the account ID from the session and rereads the database role on every request. A deleted account triggers session destruction and a login redirect for HTML, or JSON 401 with “Your account no longer exists” for API requests.

The /editor and /reporter convenience routes also send guests to login with their corresponding dashboard as next.

Sources: models/User.js, middleware/errorHandler.js, server.js, routes/pages.js, middleware/auth.js, controllers/pageController.js, views/partials/public/header-standard.ejs.

Initial rendering

2. What loads into the HTML document

staffLogin renders pages/auth/staff-login with pageTitle: "Staff Login" and a page object. It supplies the publication name, intro, labels, placeholders, return link, and next: req.query.next || "". There is no User or Article query to build this page. Session middleware can still read/write MongoDB. staffLogin and the convenience dashboard redirects use the stored session role, so visiting login with a stale session can first redirect to the old dashboard. Its protected middleware then checks the current account; a deleted account is sent back to login after session destruction.

page = {
  publicationName: "The Daily Web", publicWebsiteHref: "/",
  heading: "Staff Login", intro: "Sign in for reporters and editors.",
  next: "", // or incoming query value
  form: { usernameLabel: "Username", usernamePlaceholder: "e.g. reporter1",
    passwordLabel: "Password", passwordPlaceholder: "Enter your password",
    submitLabel: "Sign In" },
  returnLabel: "Back to public site", title: "Staff Login"
}

The page.title field is supplied but the document title uses pageTitle. Template text and attributes use escaped EJS. The page has its own centered panel, with no public header, breaking strip, footer, feed, or weather widget.

Sources: controllers/pageController.js, views/pages/auth/staff-login.ejs, views/partials/shared/head.ejs, views/partials/shared/site-logo.ejs.

Assets

3. Stylesheets and script startup

The shared head loads /css/style.css and deferred /js/api.js. The end of the page loads deferred /js/staff-login.js. The shared helper executes first, defining window.api; the login script then finds the form, inputs, button, status element, and reads form.dataset.next once.

The stylesheet imports Google font resources followed by variables → base → utilities → components → layouts → pages. Login-specific rules live in pages.css. The panel is constrained by --login-panel-width with responsive gutters and padding below 640px; a separate max-height 720px rule aligns the page from the top on short screens. Shared form controls and logo rules live in components.css. No JSON request is sent simply by loading the form; /api/auth/me exists but is not called here.

Sources: public/css/components.css, views/partials/shared/head.ejs, views/pages/auth/staff-login.ejs, public/js/api.js, public/js/staff-login.js, public/css/style.css, public/css/pages.css.

Component

5. Heading and explanation

The heading is “Staff Login” and the description is “Sign in for reporters and editors.” Both are static controller-provided strings escaped into the initial HTML. These elements have no listener, request, or later update.

Sources: controllers/pageController.js, views/pages/auth/staff-login.ejs.

Component

6. Username input

#staffUsername is required text with name="username" and autocomplete="username". Typing only changes the input value; there is no username availability request or debounce. Submission trims surrounding whitespace, preserving case. The server also trims before User.findOne; the code does not lowercase the name.

Sources: views/pages/auth/staff-login.ejs, public/js/staff-login.js, controllers/authController.js, models/User.js.

Component

7. Password input

#staffPassword uses type="password", autocomplete="current-password", and required. The browser masks its display; masking is not encryption. The script sends the raw string without trimming, so spaces can be part of the password. There is no reveal button, strength meter, remember-me control, or reset-password link in this template.

On an API or network failure, the script clears this input and focuses it. The username stays. Passwords are never returned in the success JSON.

Sources: views/pages/auth/staff-login.ejs, public/js/staff-login.js, models/User.js, controllers/authController.js.

Component

8. Sign In button and local validation

Clicking Sign In or submitting via the form first runs native required validation. If empty required inputs block submission, the JavaScript listener is not invoked. The listener prevents native navigation, trims the username, and checks both values. A whitespace-only username passes native required validation but fails this local check with “Enter a username and password.”

Before sending the request, the button is disabled and the form receives is-authenticating. Inputs remain editable. The button label stays “Sign In”; there is no inserted spinner. The CSS opacity selector targets .login-submit.is-authenticating, but the script adds the class to the form, so that particular selector does not match. Generic disabled-button styling still applies. There is no separate in-flight flag guarding programmatically dispatched submit events.

Sources: views/pages/auth/staff-login.ejs, public/js/staff-login.js, public/css/pages.css, public/css/base.css.

API contract

9. Shared API request and response parsing

The browser calls window.api.sendJSON("/api/auth/login", "POST", { username, password }). The shared helper uses fetch with same-origin credentials, JSON content type. Although request() initially builds Accept: application/json, its later options spread replaces the header object for sendJSON, so this POST uses the browser’s default Accept: */*. Existing cookies accompany the request; a successful same-origin response can update the cookie. Neither a role nor next is sent in this body.

// Illustrative request; not real credentials
POST /api/auth/login
Accept: */*
Content-Type: application/json

{"username":"example-reporter","password":"illustrative-only"}

The helper attempts JSON parsing. A non-2xx result throws an Error using body.error, or Request failed (STATUS) if absent. A fetch rejection also reaches catch. No timeout/abort is configured. A 2xx non-JSON response becomes null and causes an error when the login code reads data.redirect.

Sources: public/js/api.js, public/js/staff-login.js, server.js, routes/auth.js.

Server and database

10. Server credential verification

The controller first rejects missing/falsy username or password with 400. It looks up {username: String(username).trim()}. If no user exists, password verification is skipped. If a user exists, verifyPassword(String(password)) compares with its stored bcrypt hash. Both failures use the same 401 message, “Incorrect username or password”.

The User save hook hashes changed passwords with bcrypt cost 10; login compares only and does not rehash or save the User record. Roles are the model’s Reporter/Editor values, not supplied browser data. Unexpected database or comparison errors reach centralized API error handling, generally 500 with a generic JSON error.

Sources: controllers/authController.js, models/User.js, config/constants.js, middleware/errorHandler.js, utils/asyncHandler.js.

Persistence

11. Session and success response

On successful verification, the controller assigns req.session.user = user.toPublic(). This contains _id, username, displayName (falling back to username), and role. Express-session persists session data through connect-mongo during response handling; the controller does not call a separate save or regenerate step.

The browser carries a signed opaque connect.sid identifier, not the full role or password. Cookie settings are httpOnly, sameSite=lax, a 14-day maxAge, and secure in production. The session store is configured with a 14-day TTL. Guests also get sessions because saveUninitialized is true. Cookie/store durability was inspected in code, not verified against a live MongoDB instance.

// Illustrative Editor success response, HTTP 200
{
  "success": true,
  "user": {
    "_id": "507f1f77bcf86cd799439011",
    "username": "example-editor",
    "displayName": "Example Editor",
    "role": "Editor"
  },
  "redirect": "/editor/reviews"
}

A Reporter receives redirect: "/reporter/articles". No password/hash is returned. No token is placed in localStorage and no client role is trusted by server authorization. The session snapshots the public identity at sign-in. On later protected Reporter/Editor/Staff routes, requireRole now queries User.findById(sessionUser._id).select('role').lean(). It rejects deleted accounts with 401 and a session-destruction request, rejects disallowed current roles with 403, and writes the database role back to the session only after an allowed check. This refresh does not replace the stored username or displayName. Public login redirects and /api/auth/me still read the session without this check.

Sources: middleware/auth.js, routes/auth.js, controllers/authController.js, models/User.js, server.js.

Browser navigation

12. Destination after successful sign-in

The server supplies the default dashboard, but the browser first selects nextUrl || data.redirect. nextUrl came from the HTML data-next attribute. Exact /editor and /editor/ normalize to /editor/reviews; Reporter equivalents normalize to /reporter/articles. Exact login destinations listed in the script fall back to the response redirect. A Reporter target beginning with /editor is overridden to their dashboard.

It then calls window.location.assign, starting a new page request rather than rendering a dashboard inside the login DOM. An Editor sent to a Reporter-only route is not corrected by this script; server middleware rejects the next page with 403 after rereading the current database role.

Observed gap: next is escaped for HTML but is not checked against an internal-path allowlist. An external URL can become a navigation destination after successful login. Escaping prevents attribute injection, but does not validate where a URL points. This audit documents the behavior without changing it.

Sources: public/js/staff-login.js, views/pages/auth/staff-login.ejs, controllers/pageController.js, controllers/authController.js, routes/pages.js, middleware/auth.js.

Component

13. Feedback message and retry

#statusMessage begins empty and state-hidden, with role="status" and aria-live="polite". api.flash writes textContent, removes state-hidden, and sets color classes. The login handler also adds login-feedback-error. Messages are text, so markup in an error is not inserted as HTML.

On request failure, the password is cleared/focused and the username remains. Finally restores the button and form class. On another attempt the old message is not cleared at request start; on success the error-specific class is removed, but no success text replaces it before navigation. Despite the helper’s comment saying it clears messages afterwards, there is no timer or automatic clearing.

Sources: views/pages/auth/staff-login.ejs, public/js/staff-login.js, public/js/api.js, public/css/pages.css, public/css/utilities.css.

Error paths

14. Server failures and sign-in rate limit

Responses consumed by the login page
StatusTriggerMessage
400Missing/falsy credentials sent directly to APIEnter a username and password
401Unknown username or incorrect passwordIncorrect username or password
429IP exceeds login limiterToo many sign-in attempts. Try again in a few minutes.
500Unexpected controller errorSomething went wrong on our side. Please try again later.

The limiter allows 20 attempts per 5-minute window using the library’s default IP key and in-memory store. Both successful and failed attempts count under the installed defaults; this is not a per-username counter. It runs before credential validation/lookup. Standard rate-limit headers are enabled; legacy headers are disabled. The browser does not render a countdown or automatically retry. API failures follow the password-clearing feedback path.

Sources: routes/auth.js, middleware/rateLimit.js, controllers/authController.js, middleware/errorHandler.js, public/js/staff-login.js, package-lock.json.

Component

15. Back to public site

The return link is a normal href="/" with a decorative left arrow hidden from assistive technology. It navigates without an authentication request. It is not a logout control and does not destroy a session. The page has no logout button.

Sources: views/pages/auth/staff-login.ejs, controllers/pageController.js, routes/pages.js, public/js/api.js.

Observed behavior

16. When JavaScript is unavailable

The login form has no action or method. With scripts disabled or unavailable, native submission defaults to GET of the current page, putting username and password fields into the URL query. This does not call the POST login endpoint, create an authenticated session, or show the JavaScript feedback. The password being type=password does not prevent its submission as a query value. Do not demonstrate this with real credentials.

The controller renders the guest form again; it does not read query credentials. Existing next query parameters are not form inputs and need not survive native GET submission. The logo and return links continue working. This is an observed fallback limitation, not a recommended login design.

Sources: views/pages/auth/staff-login.ejs, public/js/staff-login.js, controllers/pageController.js, routes/auth.js.

Learning checks

17. Verification and ways to explore

Use test accounts in your own local environment. In DevTools Network, observe the initial document and assets, then the one POST after submission, followed by a document navigation after success. Compare an incorrect password with an unknown username; both should return the same 401 message. Test Reporter and Editor destinations and a protected-page redirect separately.

Verification performed for this update: static comparison of the baseline branch with HEAD, followed by a source trace of current routes, login controller, model, Mongo session setup, active EJS, browser API/login scripts, destination authorization, error middleware, rate limiter, and CSS. Documentation source and fragment links were checked. No browser tests, mocked controller checks, or live session/database tests are claimed for this update.

Limits: browser layouts, Mongo session persistence, actual limiter execution, production cookie transport, and stale-session redirect sequences were not exercised at runtime. No credentials were submitted and no application code or live records were changed. Suggested DevTools steps are manual learning exercises.
