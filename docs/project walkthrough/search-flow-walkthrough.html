Start here · HTML response

1. The user enters /search

A plain /search lists published articles, newest first. A URL such as /search?q=climate&category=Science&sort=popularity adds title search, category filtering, and popularity sorting.

Search and Apply Filters reload the page; infinite scroll appends through JSON. The visible form is not intercepted by JavaScript. A controller comment says filtering updates over Ajax, but the active template and scripts use native GET form submission.
Inputs to the page route
ParameterExampleServer behavior
qclimateTrim whitespace and search published titles, ignoring case. Regex special characters are escaped by shared escapeRegex() in utils/queries.js, so input is treated as text. Blank means no title filter.
categoryScienceExact, case-sensitive match to a configured category. Empty or unrecognized values mean All Categories.
sortpopularityPopularity sorts by totalViews descending, then publishedAt descending. Everything else uses publication date descending.

Valid categories: World, Business, Technology, Science, Culture, Sports, Opinion. The query reads publishedVersion, so approved content stays searchable while an updated draft is under review.

The page controller does not read page, search, sortBy, or seen. Those belong to the feed API contract, not the search-page form. Even /search?page=2 renders the first batch.

What exactly does the controller pass into search-results.ejs?

style.css imports Google Fonts/Material Symbols, then variables → base → utilities → components → layouts → pages. Search-specific styling belongs to .search-page* rules in pages.css. The form stacks below 640px and becomes a row at 640px; the sidebar and results stack below 1024px and become a 4:8 grid at 1024px. The console padding increases at 768px.

This page loads no weather.js, contains no weather widget, and has no separate search.js. The initial results come from the page controller directly, not a startup feed API call. The observer can request more results on startup if the sentinel is already nearby.

Server-rendered component · Native navigation

3. Header, logo, and navigation

Guests see Staff Login; signed-in staff see Newsroom and Sign Out. The mobile menu always includes Home, Search, and Staff Login. Destination newsroom routes enforce roles server-side: requireRole() looks up the session user’s current database role on each protected request. Deleted accounts lose access and their session is destroyed; a role mismatch is denied. Public search does not run this role refresh, so the header can show an older session role until protected navigation checks it.

editionLabel is passed along but is not displayed by the current header/logo markup. There is no /api/auth/me call to choose these controls.

Sources: header-standard.ejs · site-logo.ejs · role middleware

Search console · Native GET form

5. Search the Archive: input and Search button

Example with the default radios:

GET /search?q=climate&category=&sort=publishedAt

With Science and Most Popular already selected, the same button instead sends:

GET /search?q=climate&category=Science&sort=popularity
No debounce or live search belongs to this input. feed.js attaches its search listener to #feedSearch, a different hidden input. It does not listen to #searchInput or intercept #searchForm.

“Search the Archive” searches the published headline field, not the summary, article body, reporter, or unpublished drafts. The form works without JavaScript.

Sources: search console and form · title query · input listeners

Sidebar component · Radio selection → form submission

6. Category radios

All Categories uses an empty value, meaning no category constraint. Invalid or differently cased category URL values are ignored and the next render selects All Categories.

Changing a radio does not immediately fetch anything or update the result list. Its checked indicator changes natively, but .search-page__option--active is assigned by EJS and remains on the previous label until the next page render.

Sources: category radios · category validation and option mapping

Sidebar component · Database aggregation

7. Category count numbers

These are not counts for the current search term. For example, Science can show 70 beside its radio while “climate” in Science finds only 8 results. The aggregation does not use the title query or selected category.

These counts come from a single grouped query, not one database query per category. The All Categories number is also not the number of result cards currently loaded.

Sources: categoryCounts aggregation and categories locals · option-count markup

Sidebar component · Radio selection → form submission

8. Sort radios

Newest First sends sort=publishedAt and sorts by publication date descending. Missing or unknown sort values use Newest First. Sorting changes order, not the total number of matching articles.

Like category labels, the sort group’s active label styling is server-rendered and updates on submission. The browser does not sort the current result cards locally.

Sources: sort radios and hidden sort value · search sort rules

Server-rendered component · Shared article cards

11. Initial result cards

Headlines and summaries are in the document response. No client framework or second rendering system is involved. EJS escapes data; images and summaries appear only when their values exist.

Search has a remaining read-state difference: toCard() includes readLabel but omits seen, and search maps results directly through it. Initial search cards show reading time and no “Read” badge; later feed API cards include both reading time and session-based seen. The homepage now explicitly adds seen state to its initial cards, so this distinction does not apply to that page.

Both card paths use shared reporterName() from utils/viewMappers.js: displayName, otherwise username, or “Unknown” when the populated reporter account is missing. Reading time uses readingLabel(), approximately 200 words per minute, rounded with a minimum of one minute.

The page’s result list uses the shared card markup, with search-page CSS controlling its presentation. It is not a separate type of data card.

Sources: search and toCard · reporterName and readingLabel · article-card.ejs · search result styles

Hidden component · Server state → browser state

12. Hidden inputs: bridge to the feed script

These elements do not appear as controls. They let the reused homepage feed script load additional search results with the filters from the current HTML render.

The contract bridge
Page requestHidden DOM valueFeed API request
q=climate#feedSearch.value = 'climate'search=climate
category=Science#feedCategory.value = 'Science'category=Science
sort=popularity#feedSort.value = 'popularity'sortBy=popularity
Initial first batch#feedGrid.dataset.page = '1'Next observer request uses page=2.

Unsubmitted visible edits do not change scrolling results. If you type a new query or select a different category without submitting, the hidden values still describe the previous server render. Infinite scroll continues that previous search.

The hidden inputs have no name and no form association, so they are not submitted with #searchForm. feed.js attaches listeners to them, but ordinary typing/clicking in the visible controls does not fire those hidden inputs’ events.

Browser observer · JSON API · Append results

13. Infinite scroll and the feed API

The API now uses deterministic tie-breakers: newest sorts by { publishedAt: -1, _id: -1 }, and popularity by { totalViews: -1, publishedAt: -1, _id: -1 }. The search page’s initial query still omits the _id tie-breaker. Tied initial results may therefore disagree with the API order across the page-1/page-2 boundary, causing repeats or omissions. Offset pagination also does not freeze changing data or view totals.

No read/unread filter is sent from this page. The shared feed API still returns each card’s seen state from the session.

A full 20-result batch does not prove another page exists. If there are exactly 20 matches, the page still starts with hasMore=true; page 2 returns an empty array and ends the feed. Although the page controller knows the matching count, it does not use that count to calculate hasMore.

The observer may load on startup if the sentinel is already within its expanded viewport. Without IntersectionObserver or JavaScript, only the initial batch is available: there is no numbered pagination or Load More fallback. Updated pagination state lives in script variables, not rewritten grid data attributes.

Sources: observer, params, load · getJSON and request · public feed route · getFeed and buildFeedQuery

15. Empty state and loading/error status

Failures and progressive enhancement
SituationWhat the user receives
Initial /search query failsasyncHandler → errorHandler; a normal document request normally gets HTTP 500 and the error HTML page.
Feed API query failsHTTP 500 JSON { error: 'Something went wrong on our side. Please try again later.' }. Show the message in the status; keep existing cards.
API network/HTTP failureThe shared request helper throws. The feed shows the error; no automatic timer retry or retry button is implemented.
End reached after scrollingKeep all previously loaded cards; set hasMore false and show the end-of-feed message.
JavaScript disabledBoth search forms, category/sort radios, Apply Filters, the first batch, heading/count, empty state, ordinary links, and native mobile menu work. Infinite scroll and Sign Out do not run.

The status element has aria-live="polite" for announcements. It starts hidden, even when the initial batch is already the last one. api.flash() does not clear its message on a timer.

17. Staff controls and Sign Out

The server renders Staff Login for guests. Staff receive Newsroom (Editor → /editor/reviews, Reporter → /reporter/articles) and Sign Out. Newsroom is ordinary page navigation; destination middleware checks the session role.

If logout fails, the shared handler re-enables the button without showing an error message.

Learning checkpoint

20. Trace it yourself in the browser

  1. Open /search. In DevTools → Network, inspect the document response: the first cards are already HTML. With blank q, no results-count heading is displayed.
  2. Type “climate” in the main input. Confirm no request occurs just from typing. Click Search: the browser requests a new /search?q=... document and changes the URL.
  3. Select Science and Most Popular. The radio indicators change, but the cards do not. Click Apply Filters and inspect q, category, and sort in the document URL.
  4. Compare the matching result count, the initial card count (at most 20), and the global Science sidebar count. They describe different sets.
  5. Inspect #feedSearch, #feedCategory, and #feedSort in Elements. They contain the server-rendered search values.
  6. For a search with more than 20 matches, scroll near the bottom. Inspect the Fetch/XHR request for /api/articles/feed?page=2...: the API uses search and sortBy, whereas the document used q and sort.
  7. Edit the visible query or radio selection without submitting. Scroll again: appended results still follow the hidden values from the previous page render.
  8. Use the header search. Its separate form submits only q, so the category and sort return to their defaults.
  9. Search for a title that does not exist. The returned HTML includes the “No articles found” component. Disable JavaScript and submit again: the first-page search still works.
The search-page mental model: native GET forms choose the search; the server renders its first batch and counts; hidden inputs preserve that search for JSON-based infinite scroll.
