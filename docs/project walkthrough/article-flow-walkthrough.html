Start here · Public HTML page

1. The user opens /articles/:id

:id is the article’s MongoDB identifier. For example, a card link can open /articles/507f1f77bcf86cd799439011. Guests can read the page without signing in.

The public page reads the Article model directly. It does not fetch GET /api/articles/:id; that separate API is for staff editing/review. The browser also does not fetch the initial comments through the comments API.

The story comes from publishedVersion. A newer draft awaiting approval does not replace the approved public copy. Visibility is determined by isPublished, not the draft’s workflow status.

Which values does article.ejs receive? 
res.locals.currentUser = req.session.user || null

res.render('pages/public/article', {
  pageTitle: /* published title */,
  editionLabel: /* formatted server date */,
  showBreaking: true,
  breakingText: /* course-project demo notice */,
  searchQuery: '',
  categories: /* configured categories */,
  article: {
    id, title, summary, paragraphs, category,
    imageUrl, imageAlt, reporterName, initials,
    dateLabel, datetime, readLabel, views, updateCount
  },
  tags: /* category as a one-item array, or [] */,
  related: /* up to 3 toCard() objects */,
  commentsCount: /* loaded comments.length, at most 50 initially */,
  comments: /* { id, initials, author, datetime, dateLabel, text }[] */
})

These are template locals on the server. The browser receives their rendered HTML rather than this object as JSON.

Sources: server.js · page routes · articlePage and publicChrome · Article model

style.css imports fonts, then variables → base → utilities → components → layouts → pages. Article-specific presentation uses .article-page* and .article-comments* rules; shared comments use .comment-item*.

This page does not load feed.js. Related stories are a fixed server-rendered list. The shared head uses the published title as the document title; the controller does not supply a custom article-specific meta description.

Page-request side effects · Database and session

7. Views and session reading history

The hourly key rounds minutes, seconds, and milliseconds down to zero. The Analytics model has a unique article/timestamp index. These are cumulative page-request views, not unique visitors or a client-side “finished reading” event. Reloading the article counts another view.

There is no browser analytics API call on this page. Merely loading cards elsewhere does not count as a view. The view number on the article remains a static server snapshot; comment/weather updates do not refresh it.

Sources: articlePage tracking block · hourBucket and unique index · totalViews · seen/unseen feed query

Server-rendered discussion · Browser-managed count

12. Initial comments and comment count

A GET /api/comments/article/:articleId endpoint first requires a matching isPublished: true article, returning 404 for missing/unpublished articles, then returns { comments } with up to 200 comments, newest first. Invalid IDs follow central 400 handling. This page never calls it. There is no Load More, polling, or full-list refresh. Other visitors’ changes appear on a later page load. Relative time labels do not update on a timer.

Moderation flags only choose visible controls and browser handlers. The moderation API uses the session user ID to re-read the current database role on each protected request; changing data-can-moderate is not authorization.

Sources: comments query and mapping · comment partial · count and moderation initialization · listByArticle

Form submission · POST JSON · Prepend one item

15. Post Comment: request → save → update

The new item is inserted only after the server confirms success. Guest and reporter markup has no moderation actions; editor markup includes them. The delegated editor handler also works for comments added after startup.

When the initial thread was empty, EJS rendered “No comments yet. Be the first to join the conversation.” outside the list. The posting script does not remove that sentence, so it remains after the first successful post.

On a failed request, retain the entered text/name and existing comments, show the returned error in #comment-status, and restore the submit button.

Sources: submit handler and commentHtml · sendJSON and request · POST route · create

API contracts · Validation and rate limiting

16. Comment JSON and server limits

Illustrative request and response, with the response fields used by this page:

POST /api/comments/article/507f1f77bcf86cd799439011
Content-Type: application/json

{
  "authorName": "Dana Reader",
  "content": "Thanks for explaining this story."
}

HTTP 201
{
  "success": true,
  "comment": {
    "_id": "507f1f77bcf86cd799439022",
    "article": "507f1f77bcf86cd799439011",
    "authorName": "Dana Reader",
    "content": "Thanks for explaining this story.",
    "createdAt": "2026-10-06T09:00:00.000Z",
    "updatedAt": "2026-10-06T09:00:00.000Z"
  }
}

The serialized Mongoose document can also contain its version key. Unlike initial template locals, the response has _id/authorName/content/createdAt; the browser maps these to id/author/text/datetime and generates initials plus “Just now”.

Relevant comment responses
StatusTriggerPayload / outcome
201Created{ success: true, comment }; prepend one item.
400Blank / overlong content{ error: 'Comment cannot be empty' } or { error: 'Comment is too long (1000 characters maximum)' }.
404Missing or unpublished article{ error: 'Article not found' }.
429Rate limit exceeded{ error: 'You have exceeded the comment limit. You can post up to 3 comments per minute. Try again shortly.' }.
500Unexpected save/query failureCentral handler returns a generic JSON error; no new item is inserted.

The policy text says “three comments per minute”, but the configured limiter counts POST attempts by IP, across articles, including controller-rejected attempts. It is not a session/account/device quota. Its default store is process memory; it is not the Mongo-backed session store. There is no client countdown or automatic retry.

Sources: comment routes · commentLimiter · readContent and create · Comment schema

Editor-only interaction · PUT JSON · In-place update

17. Editor: Edit and Save

Editors can moderate any comment; there is no author-ownership requirement on this route. isEditor resolves the session user ID through User.findById(...).select('role').lean() on every request. Missing sessions get HTTP 401 JSON; current Reporters get 403. Deleted accounts have their session destroyed and get 401. An allowed role is copied back into the session before the controller runs. A missing comment gets 404. Neither a supplied role nor hidden controls authorize editing.

The inline editor has no Cancel control or Escape handler. On a request failure, the textarea remains with the edit and the button becomes enabled again for retry. Saving does not change the comment’s position, author, creation-time label, or count.

Sources: delegated edit handler · PUT route · isEditor · update

Editor-only interaction · DELETE JSON · Remove item

18. Editor: Delete

On failure, keep the item, show the error in the shared comment status, and re-enable the delete button. The server enforces Editor role for deletion just as it does for editing.

Deleting the last loaded comment sets the badge to 0 but does not create an empty-state sentence. The script also does not fetch an older comment to fill a slot vacated from the initial 50.

Sources: delete handler · DELETE route · remove · isEditor

19. Weather widget

// Illustrative fresh response
{
  "source": "api",
  "ageSeconds": 0,
  "data": {
    "city": "Tel Aviv", "temp": 27, "feelsLike": 29,
    "humidity": 65, "condition": "clear sky", "icon": "01d"
  }
}

Cache responses include calculated ageSeconds; stale-cache/fallback omit it. Fallback uses Tel Aviv, null temperature (displayed as --), and an unavailable condition. The response’s icon and age are not displayed.

Concurrent external lookups share an inFlight promise. Cache is process memory, not MongoDB, and disappears on restart. The 15 minutes controls cache freshness, not a browser refresh timer; the widget does not poll.

23. Errors, empty states, and no JavaScript

Failures and boundaries
SituationResponse / screen behavior
Valid ID, missing/unpublished articleThe page controller calls next(); normal document request → HTTP 404 error HTML.
Invalid MongoDB identifierCentral CastError handling → HTTP 400. Document requests get error HTML; API requests get { error: 'Invalid identifier' }.
Story/comments/related query failureasyncHandler forwards to the central error handler; normally HTTP 500 error HTML instead of the article. ValidationError maps to 400; status-bearing errors retain their status. The same wantsJson helper is shared with authorization: API URLs, XHR, or an Accept header containing application/json get JSON.
View increment failsLog the failure; asynchronous tracking does not block or replace the reading page.
POST exceeds rate limitHTTP 429 JSON; show its error, retain the draft comment, and re-enable Post Comment.
Guest/Reporter calls moderation APIHTTP 401/403 JSON from server role checks. No comment is edited or deleted.
Comment missing on Edit/DeleteHTTP 404 { error: 'Comment not found' }; preserve the loaded UI and show the error.
No initial commentsCount 0 plus server-rendered empty-state sentence. First successful post does not remove that sentence.
Last loaded comment deletedCount 0 and empty list; no new empty-state sentence is added.
Weather endpoint/network failureDisplay unavailable text in the weather widget. External-service failure instead normally yields successful stale/fallback JSON.
JavaScript disabledStory/body, metadata, initial comments, related cards, links, header search, footer, and native mobile menu work. Counter, JSON posting, moderation, logout, and weather do not run.

The comment form has no HTML action or method fallback. Without JavaScript, submitting it defaults to GET on the article URL with name/comment query fields; it does not save a comment. Visible editor buttons are type=button and do nothing without their handlers.

The shared comment status has role="status". Messages do not automatically clear on a timer. There is no background synchronization of discussion changes from other visitors.

Sources: errorHandler and notFound · asyncHandler · role errors · action outcomes · form and empty state

Learning checkpoint

24. Trace it yourself in the browser

  1. Open a published article. Inspect the /articles/:id document response in DevTools → Network: the headline, full paragraphs, related cards, and initial comments are already HTML.
  2. Check asset requests: api.js, comments.js, weather.js, CSS/fonts, and images. The startup JSON request is /api/weather; there is no initial comments-list or article-content API call.
  3. Type in Your comment and watch the remaining-character counter. Typing alone sends no request. Enter an optional name, then Post Comment.
  4. Inspect the POST URL and JSON authorName/content. Check the 201 response. The new comment appears first, the loaded-count badge updates, and the textarea clears without reloading.
  5. Try whitespace-only text. The local message appears without a POST. Server blank/length rules also apply to requests sent outside the form.
  6. Sign in as an Editor and reload the article. Click Edit: a textarea appears with no request. Click Save: inspect the PUT body/response and the text replacement.
  7. Click Delete. Cancel once to see that no request occurs; confirm another time to inspect DELETE and removal/count updates.
  8. Compare the view counter across reloads. Each page request starts increments, but the displayed number is the pre-increment snapshot. The feed API can later show this article as Read in the same session.
  9. On a thread with no comments, post one and notice the current empty-sentence behavior. On an Editor page with one loaded comment, delete it and notice that no new empty sentence is created.
The article-page mental model: the server sends the approved story and discussion snapshot, records the visit, and remembers reading history. Browser JSON actions then change individual comments and fill the weather widget.
